# MF3ZP Qwen-Assisted UAD Reference Annotation v1

**Identifier:** `mf3zp_qwen_uad_reference_v1`

**Scope:** a new data/label protocol for the already sealed 150-event MF3ZO
pilot. It is not a controller, gate, TUAD training run, confirmation, or
public-benchmark experiment.

## 1. Scientific question

MF3ZO stopped before numerical Probe A because no event had a complete,
independently verified U/A/D, Reveal, and Expiry oracle record. MF3ZP fills
that observation/label gap without changing the event population:

> Does reference U/A/D and Reveal/Expiry state add scene-generalizable
> information about exact runner-minus-native intervention utility beyond the
> current snapshot?

The MF3ZO result remains immutable. MF3ZP creates new versioned artifacts.

## 2. Fixed population and boundary

MF3ZP reuses all 150 outcome-blind MF3ZO events (75 R2R, 75 RxR, 39 raw MP3D
development scenes). It may replay their frozen native train episodes solely
to complete causal observations. It may not access consumed confirmation
scenes, `val_seen`, `val_unseen`, `test`, or `test_challenge`.

The annotation and observation stages cannot read:

- exact `delta_utility`;
- native/treatment final metrics;
- catastrophe labels;
- CAR/RCSP/DSR errors or predictions;
- scene-fold assignment;
- any future observation when labeling a prefix.

The exact outcome is first read only after every planned annotation response
has been stored and the provisional label inventory has been frozen.

## 3. Frozen-native observation completion

Each distinct selected train episode is replayed once with the frozen ETP-R1
native policy. No intervention is permitted. The replay must reproduce the
previous native action trace exactly.

At each high-level prefix the collector stores:

- a 12-view RGB panorama contact sheet;
- instruction and checkpoint/history embeddings;
- every currently executable candidate action embedding;
- opaque candidate identity, score, and relative heading;
- candidate position only in an oracle-only geometry record.

Candidate positions, future candidate sets, task metrics, and simulator pose
are forbidden inference inputs. They may only support deterministic branch
identity and Expiry labels.

## 4. Deterministic fields

For each sealed event the runner branch is identified from the original
outcome-blind MF3ZG proposal record. Across replay prefixes it is matched to
executable candidates by the frozen 0.5 m persistent-branch geometry rule.
Zero matches means absent; one means present; more than one fails closed.

- `target_in_set[t]` is generated by this programmatic identity match.
- `expiry_step` is the final prefix at which the target branch has one
  executable match under frozen-native continuation.
- `reveal_interval` is derived from target presence, semantic separation,
  and evidence closure under fixed `K=3`.
- `resolvable` is derived as Reveal end no later than Expiry.

Qwen is never asked to guess reachability, target presence, Expiry, or final
navigation benefit.

## 5. Qwen semantic reference labels

Two exact, non-rolling model snapshots independently label every planned
event-prefix:

- `qwen3-vl-plus-2025-12-19`;
- `qwen3.5-plus-2026-02-15`.

Both use temperature 0, thinking disabled, the same prompt and JSON schema,
and the DashScope OpenAI-compatible HTTPS endpoint. The provider-returned
model name must equal the requested snapshot.

Each request contains:

- the navigation instruction;
- a chronological, prefix-truncated front-view storyboard;
- the current 12-view panorama;
- opaque candidate aliases and relative headings;
- no native/runner role and no outcome.

The model reports role-blind visual distinguishability, unique
instruction-supported candidate, decisive instruction spans, decisive past
frame indices, and whether future evidence is still required. Program code
then projects the response onto the sealed runner/native pair:

- `candidate_separated[t]` requires the target and native candidates to be
  visible and distinguishable;
- `evidence_closed[t]` requires a uniquely supported target, separation,
  decisive text/frame evidence, and no stated need for future evidence.

Natural-language confidence is not used as a probability.

## 6. Qwen-only exploratory scout

The two model-specific provisional label sets may each run the already fixed
MF3ZO Probe-A ridge computation. This result is explicitly exploratory:

- `EXPLORATORY_QWEN_ORACLE_SIGNAL_POSITIVE` only if both annotators
  independently satisfy both per-domain Delta-Huber and scene-bootstrap
  criteria;
- otherwise `EXPLORATORY_QWEN_ORACLE_SIGNAL_NOT_POSITIVE`.

Neither status is a formal identifiability PASS, authorizes TUAD, or permits a
public evaluation. The scout may guide whether human audit is worth the cost,
but it cannot tune prompts, labels, features, models, thresholds, folds, or
regularization.

## 7. Human verification gate

Machine agreement is not human ground truth. Formal Probe A remains disabled
until blind human review covers:

- 100% of events on which the two Qwen snapshots disagree;
- a deterministic domain/scene-balanced sample of 40 agreement events.

Two human reviewers label independently without outcomes. A third human
adjudicates their disagreements. Before adjudication, agreement must satisfy:

- U/A/D Cohen kappa at least 0.65;
- evidence-closure Cohen kappa at least 0.70.

The same thresholds apply to each Qwen snapshot against adjudicated human
labels on the audited sample. Failure is
`REFERENCE_LABEL_VALIDITY_FAIL`; it may not be repaired by prompt/model
search on these events.

Only an independently versioned authorization after this gate may construct
formal verified oracle labels and run formal MF3ZO Probe A.

## 8. One-shot rules

The event population, two model snapshots, system prompt, response schema,
image construction, K, automatic identity rule, fixed MF3ZO folds, ridge
L2=1, bootstrap scheme, and PASS/FAIL definitions are sealed before
collection or annotation.

Transport/schema failures use fixed identical-request retries. Every planned
request must resolve before the scout; there is no outcome-dependent stopping.
After seeing any semantic or Probe-A result, MF3ZP may not change its prompt,
model, label definition, feature set, or thresholds.

No MF3ZP outcome can generate a deployment checkpoint.
