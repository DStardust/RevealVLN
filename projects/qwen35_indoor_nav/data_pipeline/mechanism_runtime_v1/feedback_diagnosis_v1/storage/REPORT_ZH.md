# 特殊数据 run_v1：存储与持久化离线诊断

结论：**优先优化预算日志的重复持久化，而不是再改已经加速的 ContentStore；但现有日志不足以证明“总墙钟的大多数就是 fsync”。** 建议先做不触及标签、轨迹和安全门槛的单次动作预算提交合并，再给下一版本补精确计时。存储提速不能修复第二个场景的构造失败，也不能使零合格族自动转为合格。

本任务只读已经结束的 `feedback_generation_v1/run_v1` 和源码，未启动仿真、GPU 查询、训练、基准测试或任何进程控制，未修改原运行目录、INPUT_LOCK 或 STATUS。普通数据后台未触碰。

## 2. 持久化调用为什么应优先排查

源码 [runtime_journal.py](../../runtime_journal.py) 每次成功 append 都有三次同步提交：events 文件 fsync、临时 HEAD 文件 fsync、替换 HEAD 后的目录 fsync。由已验证的 85,897 条成功记录推导出 **257,692 次 fsync 调用路径**，含初始化父目录一次。

原 [guard.py](../../guard.py) 对每个新增 NPY 文件也有三次 fsync；7,455 个成功内容文件对应 **22,365 次**。本轮 store 未 poisoned、无失败 journal，最终两次审计均通过。两类合计 280,057 次，journal 占 **92.014%**。

以上是**实际记录数量 × 已读成功源码路径**的调用次数推导，不是 strace/perf 捕获的 syscall 计数，更不是实际 IO 等待秒数。

每次运动通常伴随约五条 budget 持久化和一条 action_completed；budget.check_time 不只是查时钟，还完整提交快照。reserve_action 自身又做“check_time 提交一次 + 增加动作预算提交一次”。这一模式使小日志同步调用数量远高于图像新文件提交。

当前运行**已经使用 TrackedContentStore**，成功路径不再逐帧扫描全目录。本次不能把它的既有改进又算成尚可获得的新收益。ContentStore 仍严格检查重复文件内容；仅从已保存观测可推导至少 28,570 次 put，减去 7,455 个新文件后，至少 21,115 次是重复内容访问。不能为了加速直接去掉碰撞或篡改检查。

## 3. 现有时间戳真正能证明多少

预算快照记录的是调用 check_time 时的单调时钟，**早于该次同步提交**。通过相邻 action_completed 之间严格限定“恰好五条 budget、同 bundle、同执行模式”的序列，并映射源码控制流，可以分离两类窄间隔：

| 间隔 | 数量 | 合计 | 中位数 |
|---|---:|---:|---:|
| 普通 replay：动作后 checkpoint → observe 入口 checkpoint | 12,693 | 142.424 秒 | 10.670 ms |
| feedback：observe 后 checkpoint → 下次 while 入口 checkpoint | 1,235 | 13.859 秒 | 10.790 ms |

这些互不重叠的间隔合计 **156.284 秒，占总墙钟 12.436%**。每个含一次同步 budget journal 提交及邻接 Python 控制/验证，不含新的仿真 step 或下一次像素存储。因此已有证据足以确认“高频 checkpoint 有实质成本”。

但它们**不等于纯 fsync 时间**；不能把 11.2 ms 的均值直接乘以所有日志条数，宣称测得了 900 多秒 IO。未分类时间仍包含其他 journal、渲染、寻路、像素处理、存储、证书检查与 JSON 序列化。

231 次原 GPU 利用率快照均值约 1.81%、中位数 0，也只能支持“这些采样时刻 GPU 不饱和”。原 compute-apps 清单漏 G renderer，瞬时利用率不能用于证明 GPU 总耗时很少。原 supervisor 做了 19 次全目录字节盘点，未记录它们各自耗时。

## 4. 最小、不降低质量的下一版本

### 优先 P1：将一次 reserve_action 的两次预算提交合为一次

限定改动：新版本预算类内部读取时钟、检验单调性和时限/动作上限，再将同一时刻的 clock 和动作计数一起持久化；**成功落盘并更新 HEAD 之后才能调用 backend.step**。

- 合法动作的最终预算状态必须与旧类完全相同。
- 预算拒绝分支仍保留对应 clock 状态及拒绝原因，不能越限后执行。
- 持久化失败保持 poisoned，后端调用次数为零；任何已保守预扣动作不可退还或重置。
- 不修改原类，只在新版本实现并声明日志逻辑记录数量变化。旧日志不是新日志逐字节一致的对照，比较的是最终预算状态、前调用安全不变量与动作序列。
- 按本轮 14,205 个成功动作，理论可少 14,205 个 append / 42,615 次 fsync 路径。**这是调用数量节省，不是已经测得的时间加速。**

比起将所有 check_time 改成不持久化，这一改动更小，不需要放弃 action 前耐久预算和每次检查的时钟契约。更激进的跨动作批量预留/异步日志暂不优先，因为它们改变崩溃后的计数、确认边界或暂停语义。

### 优先 P2：完整审计只做一次，并在关闭后接收结果

当前 worker 显式 `full_audit()`，随后 context close 又做一次完整读取/hash，两次共读约 2.518 GB 内容。下一版本可以仅让 close 做完整审计，在退出 context 后检查 final_audit 并写入接收产物；不得把关闭前的未审计状态发布成合格数据，也不允许审计后继续写。只去掉重复审计，不去掉最后一次逐文件校验。可省一遍完整内容读取，但具体秒数未测量。

### 同步修复证据完整性：中断 trace 明确落盘

TraceRunner 在资源截断或异常的 finally 保存已实际观察/执行的部分轨迹，并强制 `complete=false`、明确 error 和预算信息，不猜测缺失观测，不将它加入训练认证。保留旧的 61 动作缺口事实，不补写旧运行。此修复是证据质量改善，不是加速收益。

## 5. 必须先做的验证

1. **CPU 状态等价**：正常/边界/拒绝/同相位重入，用可控 clock 对照旧预算类；正常调用结束快照、总计、相位计数一致。
2. **CPU 崩溃注入**：event 写入前后、event fsync、HEAD 写入/替换/目录 fsync 每个阶段注入异常；后端绝不能在未确认预算后运行，恢复不得忽略尾记录或返还预扣数。
3. **调用计数**：计数器而非真实 GPU验证“每合法 reserve 少一次 append”，独立 CPU 同序列真实 fsync 对照另准入；报告总墙钟与 p50/p95，不先承诺加速倍数。
4. **新版本真实运行加计时**：给 journal.append、content.put、backend.step/reset、path/follower、compiler 和最终 audit 分别记录 count/累计/最大耗时；以不相互嵌套的阶段标签统计，避免重复相加。原 run 没有这些计时，不可事后编造。
5. **质量不退化**：同候选、同几何、同种子、同逻辑动作预算、同完整认证门槛。时间预算不变时允许因速度更快探索更多候选，但必须分别报告“固定动作预算等价”和“固定墙钟吞吐”，不能把更多搜索预算冒充单样本算法收益。

最终判断：日志层是**有直接证据、最值得先优化的工程点**；本轮不能给出精确的全局耗时分解，也没有证明任何新机制收益。第二场景仅 2.677 秒、零动作就穷尽配置，必须由构造/语义诊断支线处理，存储优化对此无帮助。
